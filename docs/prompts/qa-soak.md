# QA 浸泡测试 Prompt —— 自主多轮使用测试（使用问题 + 交互体验）

> 给执行本任务的 agent：本文件自足。这是一次**只测不改**的浸泡测试：你的任务是以真实用户的
> 方式把焊接助手反复用很多遍，挖出「使用过程中会踩到的问题」和「交互体验摩擦」，留证、定级、
> 成报告。产品代码一律不修改（发现 bug 只记录；除非用户在本次会话里明确让你修）。
> 总则：每个确认的问题必须有独立复现（≥2 次）与证据文件路径；没跑过的轮次不许写进报告。

## 背景与产品概貌

「焊接助手」是给焊接工人在台前**单手操作**的手机 PWA（Preact + Vite + PWA，另有 Capacitor
安卓壳）。核心链路：导入转换好的 STJ 任务文件 → 报菜名屏（手动点选决定取料顺序，或用
「AI 排序」输入一句话让 DeepSeek 排）→ 校准 → 焊接执行（当前元件卡片：完成/跳过/撤销，
卡片上滑=跳过；全屏九宫格地图报区域词；TTS 播报）→ 收尾清单（被跳过的件）→ 总结页。
设置页有：TTS（音色/简洁模式等）与「AI 排序」（API 地址 / Key / 模型，Key 只存本机）。
断点续焊：进度与排序持久化在 IndexedDB，中途关页应能恢复。

## 驱动方式与取证

- 用可用的浏览器自动化技能（`web-gui-tester` / `control-browser`）驱动真实浏览器。
- **全程移动端视口**（如 390×844，启用 touch 模拟）——这是手机竖屏应用，桌面宽屏不在验收范围。
- 历史教训（m5-friction F5）：注入点击可能静默丢失。**每步操作后必须读屏验证生效，失败重试一次**；
  重载/跳转后等 ≥3s 再操作。
- 每轮截图存 `docs/qa/soak-2026-10-24/`（命名 `<轮次>-<步骤>.png`）；控制台 error/warning 全程
  捕获并记录（截图 + 文字），一个都不许漏记。
- TTS 在桌面浏览器听不到真音，验证口径：播报触发时无 JS 报错、扬声器状态/队列 UI 正确、
  设置项开关生效；真实音色与节奏留给实机测试，报告里注明此边界。

## 轮次安排（≥14 轮，全部跑完；每轮开始前明确本轮目标）

**A 组 · 正常路径（3 轮）**：demo / boardA / boardB 各完整走一遍 导入→报菜名→校准→焊接→收尾→总结。
记录每步等待感（>2s 的转场都算摩擦候选）。boardB 必须包含双面翻面与「整组焊接」询问路径。

**B 组 · 中断与恢复（3 轮）**：
1. 焊到约 1/3 时直接刷新页面 → 断点续焊恢复，进度/排序/校准状态是否原样；
2. 焊接中另开第二个同源标签页再操作，两边轮流刷新（回归 F3 IndexedDB 升级阻塞假死）；
3. 报菜名排好序 → 校准中途返回首页 → 重进；设置改完立即焊接（配置是否即时生效）。

**C 组 · 异常与边界（4 轮）**：
1. 导入坏文件（空/截断/非 JSON/图片改名），报错是否明确、能否原地重选；
2. AI 排序失败矩阵：未配 Key、错 Key（期望 E_AI_HTTP 文案）、断网（E_AI_NETWORK）、
   内网或 http 地址（E_AI_URL 拦截）、30s 超时（可用可控慢速桩模拟）——**每次失败后确认手动
   点选顺序纹丝不动、可直接「下一步」**；
3. 极端操作序列：boardB 全部跳过 → 收尾清单 108 项；逐颗全部撤销到第 1 颗；跳过→撤销→再跳过；
   校准后手动旋转设备方向（若模拟器支持）；
4. 快速连点与抢跑：完成连点、跳过连点、完成+撤销交替快速点，状态机是否错位、TTS 是否堆积。

**D 组 · 交互压力（2 轮）**：
1. Monkey：在焊接执行屏随机乱点/乱滑 ≥200 次事件，期间穿插返回键与刷新，要求不白屏、不卡死、
   刷新后可恢复；
2. 手势边界（回归 F2）：上滑跳过用 600ms 慢速、120ms 快速、斜向、极短位移分别测；触屏模拟与
   鼠标拖拽两种输入都测；确认滑动不会误触成「完成」。

**E 组 · AI 排序正常路径（2 轮）**：
1. 若环境有真实 DeepSeek Key（问用户要；没有则用本地 mock OpenAI 兼容服务），测 3 类指令：
   「先焊电阻，IC 和接插件放最后」「按我袋子从上到下：100nF、ME6211、10k」「随便排」，
   校验序号角标、取料序预览、持久化；
2. mock 返回畸形回复矩阵：markdown 围栏包裹、缺 gid、重复 gid、多/少组、非 JSON、纯文本——
   全部应红字报错（E_AI_FORMAT / E_AI_PERM）且不影响手动排序。

## 交互体验评审（每轮结束打分 1–5 并写一句依据，报告汇总成表）

1. 首次上手：不看文档能否走通全流程？哪里迟疑？
2. 文案可操作性：每个报错是否告诉用户「下一步该干什么」？
3. 误操作恢复：跳过/撤销/返回是否总能回到一致状态？有没有「回不去」的死路？
4. 焊接中可读性：模拟离屏 40cm 看卡片——关键字段（位号/值/序号/区域词）一眼可得吗？
5. 触控目标与单手可达：主按钮位置、尺寸是否适合持焊台操作？滑动热区是否过大/过小？
6. TTS 与画面同步：播报节奏是否会落后于操作？连点时是否堆叠？
7. 地图九宫格区域词：能否真的帮用户找到元件位置？
8. 反馈与转场：所有 >1s 的等待有没有加载反馈？转场有没有突兀闪动？
9. 深色主题对比度：截图里检查小字与角标可读性。

## 判定与记录标准

- 严重度：S1 = 崩溃/白屏/数据丢失/状态机错位；S2 = 功能不可用、误导性文案、恢复失败；
  S3 = 摩擦与体验问题（含所有 >2s 等待、文案含糊、热区问题）。
- 每个问题：编号 + 一句话标题 + 复现步骤（精确到点哪个按钮）+ 期望 vs 实际 + 证据路径 +
  出现次数（**≥2 次才算「确认」，1 次标「flaky 待复验」并再跑 2 次**）+ 严重度 + 修复建议。
- 疑似根因可以写（读代码定位），但**不许动代码**。同类问题去重合并，跨轮次重复出现要标注轮次号。

## 输出与完成标准

- 证据：`docs/qa/soak-2026-10-24/`（截图 + `console.log` 摘录）。
- 报告：`docs/qa/soak-2026-10-24-report.md`，结构对齐 `docs/m5-friction.md` 的风格：
  结论先行（问题总数按严重度分布）→ 确认问题清单表 → flaky 待复验清单 → 体验评分表（9 项）→
  「本轮未覆盖/留给实机」边界说明。
- 完成标准：14 轮全部执行、每个确认问题有 ≥2 次独立复现与证据、报告落盘、
  控制台错误 100% 归档。跑完在报告末尾给出「建议立即修的 top 3」。
